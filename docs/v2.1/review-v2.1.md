### ⚠️ 评审点 2：新计分公式实现是否正确

**公式**：`(BASE_CHIP + chipBonus) × (baseMult + multBonus)`

**结论：公式实现正确，但存在一处逻辑偏差。** ⭐

代码（`index.html` 第 1241~1244 行）：
```js
const baseChip  = GAME_CONFIG.BASE_CHIP;   // 10
const totalChip = baseChip + chipBonus;
const totalMult = baseMult + multBonus;
const cellScore = totalChip * totalMult;
```

✅ 公式本身完全正确。

⚠️ **问题 P2-1：同一方块只能生效一张小丑牌**

当前实现中，每个方块的 `joker` 字段只能存储**一张**小丑牌（`cell.joker = { ...joker }`）。如果一个方块同时满足多张牌的触发条件（比如既有颜色牌又有几何大师），只有最后附着的一张会生效。

- 这在当前的自动附着逻辑中通过 `usedPositions` 避免了同一方块被多张牌附着（第 761 行），因此**不会产生实际 bug**。
- 但手动附着模式下（`attachJokerToCell`），如果方块已有其他牌（不同 ID），会被**直接覆盖**（第 913 行 `cell.joker = { ...attachingJoker }`），原有的牌会丢失，且无任何提示。

**建议**：手动附着时应提示玩家"该方块已附着了 XXX 牌，是否替换？"，或阻止覆盖并给出反馈。

### ⚠️ 评审点 3：基础倍率判定逻辑是否正确（方向数 = 基础倍率）

**结论：单次消除正确，但连锁消除（combo）存在方向信息丢失问题。** ⭐

代码（第 1147~1148 行）：
```js
const dirCount = (hasHorizontal ? 1 : 0) + (hasVertical ? 1 : 0) + (hasDiagonal ? 1 : 0);
const baseMult = Math.max(1, dirCount);
```

✅ 单次消除的方向判定逻辑正确：`dirCount` 为 1~3，`Math.max(1, dirCount)` 保证最低为 1。

⚠️ **问题 P3-1（低风险）：连锁消除时方向信息是独立的**

连锁消除（combo 2、3...）时，每次 `processMatches` 递归调用前会重新执行 `findMatches()`（第 1302 行），返回的方向信息是**该轮独立的方向信息**。这意味着第一次消除是横向+竖向（×2），连锁消除只有横向（×1），两轮的基础倍率是各自独立的。

- 策划文档说"**针对整次消除**，所有方块统一"，这里的"整次消除"指的是单轮消除内的所有方块共用一个基础倍率，而非跨连锁轮次共用。
- 当前实现**每轮独立计算**，从策划意图来看是合理的（连锁的每一波是独立的消除事件）。

> ✅ **基本通过**，但建议与策划确认连锁场景下"整次消除"的定义边界。

### ⚠️ 评审点 6：计分展示面板的展示内容和节奏是否符合策划要求

**结论：整体结构符合，但有两处与策划细节不一致。** ⭐

#### ✅ 符合部分

| 策划要求 | 实现情况 |
|---------|---------|
| 方向判定行先出现（约 300ms） | ✅ `await sleep(50)` 后淡入 + `await sleep(300)` 等待 |

| 有卡牌加成的部分用对应颜色高亮 | ✅ `sp-bonus-*` CSS 类 |

#### ⚠️ 问题 P6-1（中等）：面板展示格式与策划示例有差异

策划要求的展示格式：
```
🟥 基础分 10 × (2 +3 ♥红莲之心) = 50
```

实际代码生成的格式（第 1391~1393 行）：
```js
multStr = `(<span class="${bonusCls}">${row.baseMult} +${row.multBonus} ${jokerSymbol}${jokerName}</span>)`;
```
渲染结果：`(2 +3 ♥红莲之心)` — 整个括号内容都被高亮成一个颜色，包括 `baseMult` 数字。

而策划的意图是**只有加成部分**（`+3 ♥红莲之心`）用卡牌颜色高亮，`baseMult`（2）应为默认颜色。

**建议修改为**：
```js
multStr = `(${row.baseMult} <span class="${bonusCls}">+${row.multBonus} ${jokerSymbol}${jokerName}</span>)`;
```

#### ⚠️ 问题 P6-2（低风险）：面板淡出后 `visible` 类未移除

`showScorePanel` 在结尾设置定时器添加 `fadeout` 类（第 1417 行），但从未移除 `visible` 类。CSS 中：
```css
.score-panel.fadeout { opacity: 0; transition: opacity 0.6s ease; }
```

由于 `.fadeout` 的 `opacity: 0` 会覆盖 `.visible` 的 `opacity: 1`（两者特异性相同，后声明的 `.fadeout` 优先），视觉上可以正常淡出。但这依赖 CSS 声明顺序，如果后续有人调整 CSS 顺序可能导致面板无法正常淡出。

**建议**：淡出完成后通过 `transitionend` 事件移除 `visible` 类，或在下次 `showScorePanel` 开头显式移除 `fadeout` 和 `visible`（当前代码已在第 1351 行移除 `fadeout`，这一点做得好）。

### 🔴 评审点 8：潜在 bug 排查

#### 🔴 BUG P8-1（严重）：交换无匹配时不回滚，白白浪费步数

代码（`onCellClick` 第 1046~1058 行）：
```js
[board[sr][sc], board[r][c]] = [board[r][c], board[sr][sc]];
moves--;
updateUI();
renderBoard();
await sleep(200);

const matchResult = findMatches();
if(matchResult.cells.length === 0) {
    checkGameState();    // 直接检查游戏状态
    isProcessing = false;
}
```

**当交换后没有产生任何匹配时，代码不会将方块换回原位**。步数已扣减，棋盘状态已改变，但消除并未发生。这与消除类游戏的通用规则不符 — 通常无效交换应回滚。

**影响**：玩家可能无意义地消耗步数，体验极差。

**建议**：
```js
if(matchResult.cells.length === 0) {
    // 无匹配，回滚交换并恢复步数
    [board[sr][sc], board[r][c]] = [board[r][c], board[sr][sc]];
    moves++;
    updateUI();
    renderBoard();
    isProcessing = false;
}
```

> ⚠️ **注意**：这个问题可能是从旧版本就存在的，需要确认策划意图。如果策划明确要求"交换即扣步数，无论是否匹配"，则此处合规。但 changelog 的"不变的部分"未提及此行为，建议与策划确认。

#### ⚠️ BUG P8-2（中等）：几何大师的触发条件"5连消及以上"使用 `group.length` 而非全局 size

代码（第 1169 行）：
```js
const size = group.length;
```

`group` 是按颜色分组后的方块集合。`size` 代表的是**同一颜色在本次消除中被消除的方块数**。

策划说"5连消及以上时触发"。如果一次消除涉及 4 个红色 + 4 个蓝色 = 8 个方块，但每组只有 4 个，`size` 为 4，几何大师不会触发。但如果策划的"5连消"指的是"同一颜色有 5 个以上方块被消除"，则当前实现是正确的。

**歧义点**："5连消" 是指：
- (A) 单次消除中**同色方块** ≥ 5（当前实现）
- (B) 单次消除中**所有方块总数** ≥ 5

从三消游戏的通用语义来看，"5连消"更倾向于 **(A) 同色 5 连**，当前实现合理。但建议在策划文档中明确定义。

#### ⚠️ BUG P8-3（中等）：面板同时显示 chipBonus 和 multBonus 时，只高亮一张卡牌的颜色

当前代码中 `jokerForPanel` 只能存储一张卡牌（第 1218 行）：
```js
let jokerForPanel = null;
```

如果一个方块的卡牌**同时**提供了 chipBonus 和 multBonus（目前不可能，因为每张卡只提供一种），不会有问题。但如果未来有新卡牌同时提供两种加成，面板只会显示最后一张卡牌的名字和颜色。

当前版本无实际影响，但代码扩展性不足。

#### ⚠️ BUG P8-4（低风险）：连锁消除时计分面板快速覆盖

当发生连锁消除（combo 2、3...）时，每轮都会调用 `showScorePanel`（第 1264 行）。上一轮面板可能还在展示中，就被新一轮的面板内容覆盖。

当前代码通过 `clearTimeout(scorePanelTimer)` 清除上一次的淡出定时器（第 1348 行），并重置面板状态（第 1351~1356 行），所以不会造成 DOM 残留。但**玩家可能来不及看完上一轮的计分明细**。

**建议**：连锁消除时，可以考虑将多轮明细累积在面板中（分隔显示），或者等上一轮面板展示完毕后再开始下一轮。

#### ✅ 其他边界检查

| 检查项 | 结果 |
|--------|------|
| `board[r][c]` 的 null 检查 | ✅ `findMatches` 和 `processMatches` 中均有 `if(!cellData) continue/return` |
| `GAME_CONFIG.BASE_CHIP` 未定义时 | ✅ 已在 `config.js` 中定义，默认值 10 |
| `inventory` 为空时 | ✅ `autoAttachFromInventory` 第 741 行有 `if(inventory.length === 0) return` |
| `board` 未初始化时调用 `renderBoard` | ✅ `cancelAttachMode` 第 733 行有 `if(board.length > 0)` 保护 |
| `availableColors` 被过滤为空数组时 | ⚠️ 理论上 5 种颜色排除最多 4 种（横/竖/两对角），不会为空。但极端情况下如果排除逻辑累积，可能返回空数组导致 `undefined`。低概率，可容忍。 |
